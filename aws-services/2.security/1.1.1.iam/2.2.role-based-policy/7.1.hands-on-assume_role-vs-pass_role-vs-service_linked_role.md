# 🎭 1) AssumeRole — *You become the role (temporary creds)*

## Best use case

**Cross-account human access** (or CI job) where you need to act in **Account B** briefly—for reads, writes, deployments—*as if you were there*.

## What you’ll build

* A role in **Account B** that **trusts** a principal from **Account A**.
* You’ll call `sts:AssumeRole`, export temporary credentials, and run commands.

### A. Create role in Account B (trusted by A)

**Trust policy (Account B → RoleB_OperatorTrust):**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::A_ACCOUNT_ID:user/Hady" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "safe-external-id-123" }
    }
  }]
}
```

**Permissions policy for RoleB (what you can do while assumed):**
*(example: read BucketB & describe EC2)*

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:ListBucket"], "Resource": "arn:aws:s3:::BucketB" },
    { "Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::BucketB/*" },
    { "Effect": "Allow", "Action": ["ec2:DescribeInstances"], "Resource": "*" }
  ]
}
```

### B. Assume the role from Account A and use it

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::B_ACCOUNT_ID:role/RoleB_OperatorTrust \
  --role-session-name hady-xaccount \
  --external-id safe-external-id-123 > /tmp/assume.json

export AWS_ACCESS_KEY_ID=$(jq -r .Credentials.AccessKeyId /tmp/assume.json)
export AWS_SECRET_ACCESS_KEY=$(jq -r .Credentials.SecretAccessKey /tmp/assume.json)
export AWS_SESSION_TOKEN=$(jq -r .Credentials.SessionToken /tmp/assume.json)

# Test access in Account B (works as the role)
aws s3 ls s3://BucketB
aws ec2 describe-instances --region eu-central-1
```

### Security tips

* Use **ExternalId** (or MFA) for cross-account trust.
* Scope the role permissions tightly.
* Rotate out of the temporary creds when done (`unset AWS_*`).

# 🪄 2) PassRole — *You let a service use a role*

## Best use case

**Attaching an execution role to a service** (Lambda, ECS Task, EC2 instance profile, Glue job). The **service** needs permissions at runtime (e.g., read S3, write CloudWatch Logs).

## What you’ll build

* An **execution role** with a **trust policy** that allows the **service** to assume it.
* Your **user** will have `iam:PassRole` permission so you can attach that role to the service.
* A Lambda function using that role.

### A. Create the execution role for Lambda

**Trust policy (service principal):**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "lambda.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

**Permissions policy for the role (what Lambda can do at runtime):**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["logs:CreateLogGroup","logs:CreateLogStream","logs:PutLogEvents"], "Resource": "*" },
    { "Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::BucketB/*" }
  ]
}
```

### B. Give *you* permission to pass that role

*(Attach to your user/role in Account A)*

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "iam:PassRole",
    "Resource": "arn:aws:iam::A_ACCOUNT_ID:role/LambdaExecutionRole",
    "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } }
  }]
}
```

### C. Create a Lambda and attach the role

Prepare a simple function:

```bash
zip function.zip lambda_function.py
```

**lambda_function.py**

```python
def handler(event, context):
    return {"ok": True}
```

Create the Lambda (service will assume the role at runtime):

```bash
aws lambda create-function \
  --function-name demo-passrole \
  --runtime python3.12 \
  --handler lambda_function.handler \
  --zip-file fileb://function.zip \
  --role arn:aws:iam::A_ACCOUNT_ID:role/LambdaExecutionRole
```

Invoke to verify:

```bash
aws lambda invoke --function-name demo-passrole /tmp/out.json && cat /tmp/out.json
```

### Security tips

* **Always** restrict `iam:PassRole` by **specific role ARNs**, not `"*"` .
* Add `Condition` `iam:PassedToService` to lock it to one service.
* Keep runtime permissions in the execution role minimal.

# 🧱 3) Service-Linked Role (SLR) — *AWS creates & manages its own role*

## Best use case

**AWS service needs to manage resources on your behalf** (Auto Scaling launching instances, CloudWatch publishing metrics, ECS, ELB, etc.). You don’t want to design the role—AWS provides a **pre-wired role** with the exact trust & permissions.

## What you’ll build (and check)

* Trigger/create a resource that **auto-creates** its SLR.
* Verify the SLR exists and see how it’s used.

### A. Example: Auto Scaling SLR

When you create an Auto Scaling Group (ASG), AWS may create:

```
AWSServiceRoleForAutoScaling
```

Check SLRs:

```bash
aws iam list-roles --query 'Roles[?contains(RoleName, `AWSServiceRoleFor`)].RoleName'
```

If missing, you can create explicitly:

```bash
aws iam create-service-linked-role --aws-service-name autoscaling.amazonaws.com
```

Then create an ASG (simplified example with an existing launch template):

```bash
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name demo-asg \
  --min-size 1 --max-size 2 --desired-capacity 1 \
  --vpc-zone-identifier "subnet-abc123,subnet-def456" \
  --launch-template "LaunchTemplateName=my-template,Version=1"
```

The **service** (Auto Scaling) uses its **SLR** to:

* Launch/terminate EC2 instances
* Attach to target groups, etc.

### Security tips

* SLRs are **managed by AWS**: don’t attach random policies.
* Use **IAM Access Analyzer** & **CloudTrail** to audit usage.
* Delete only if the service no longer needs it:

```bash
aws iam delete-service-linked-role --role-name AWSServiceRoleForAutoScaling
```

*(AWS may block deletion while the service still relies on it.)*

## 🧭 Quick chooser

| Need                                                      | Pattern                 | What you do                                                                        |
| --------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------- |
| You (human/CI) need temporary access in another account   | **AssumeRole**          | Create trusted role in target, `sts:AssumeRole`, use temp creds                    |
| A service needs runtime permissions (Lambda/ECS/EC2/Glue) | **PassRole**            | Create execution role (trusts service), grant yourself `iam:PassRole`, attach role |
| An AWS service must manage resources for you              | **Service-Linked Role** | Let AWS auto-create SLR; you just create/use the service resource                  |

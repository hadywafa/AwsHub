Let’s unpack this clearly and simply, because this is **the #1 place** people mix up `AssumeRole` and `PassRole`.

---

# 🎭 First — What “Principal” Means

In AWS IAM:

> A **Principal** is **who** or **what** is allowed to **assume** or **use** a role.

That “who” could be:

* a human IAM user 👤
* another role 🎭
* an AWS service 🤖 (like `lambda.amazonaws.com`, `ec2.amazonaws.com`, etc.)

---

# 🧩 When You Create a Role for a Service

Let’s say you create a role that **Lambda** will use —
you set **Lambda** as the *principal* in the role’s **trust policy**:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "lambda.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

✅ This means:

> “The **Lambda service** is allowed to call `sts:AssumeRole` on this role.”

So yes — the **service is the principal** here!
That’s how you let Lambda (or EC2, ECS, etc.) *become* that role when running your code.

---

# 🧠 Here’s the Subtle Difference:

| Case                                                      | Who Assumes the Role? | Who Must Be Allowed as Principal?                          | Who Needs `iam:PassRole`?                 |
| --------------------------------------------------------- | --------------------- | ---------------------------------------------------------- | ----------------------------------------- |
| You assume the role directly                              | 🧑‍💻 *You*           | `Principal: { "AWS": "arn:aws:iam::A:root" }` or your user | ❌ Not needed                              |
| Lambda (or EC2, ECS, etc.) assumes the role automatically | 🤖 *The service*      | `Principal: { "Service": "lambda.amazonaws.com" }`         | ✅ You need `iam:PassRole` to hand it over |

---

# 🧠 So Why Both?

* **Trust policy** (with `"Service": "lambda.amazonaws.com"`)
  → tells AWS **who is allowed** to assume the role (the service itself).

* **PassRole permission**
  → tells AWS **who can attach** or **hand over** that role to the service.

> ✅ You (the user) need `iam:PassRole`.
> ✅ The service (Lambda/EC2/ECS) needs `sts:AssumeRole` allowed in the role’s trust policy.

---

# 🔐 Example: End-to-End

### 1️⃣ The Role (trusted by Lambda)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "lambda.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

### 2️⃣ Your User Permissions

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Action": "lambda:CreateFunction", "Resource": "*" },
    { "Action": "iam:PassRole", "Resource": "arn:aws:iam::123456789012:role/MyLambdaRole" }
  ]
}
```

✅ Then your CLI command works:

```bash
aws lambda create-function \
  --function-name my-fn \
  --role arn:aws:iam::123456789012:role/MyLambdaRole \
  --runtime python3.12 \
  --handler lambda_function.handler \
  --zip-file fileb://function.zip
```

If you skip `iam:PassRole`, AWS blocks you with:

```
User is not authorized to perform: iam:PassRole
```

# 💬 TL;DR (Easy Memory Trick)

| Concept                     | Who assumes?                      | What policy controls it?                                          | Example Principal                            |
| --------------------------- | --------------------------------- | ----------------------------------------------------------------- | -------------------------------------------- |
| **AssumeRole**              | You become the role               | Trust policy → `Principal: { "AWS": "your user or role" }`        | `"AWS": "arn:aws:iam::111:user/Hady"`        |
| **Service Role (PassRole)** | AWS service becomes the role      | Trust policy → `Principal: { "Service": "lambda.amazonaws.com" }` | `"Service": "ec2.amazonaws.com"`             |
| **PassRole permission**     | You let the service use that role | Your IAM policy → `Action: iam:PassRole`                          | `"Resource": "arn:aws:iam::111:role/MyRole"` |

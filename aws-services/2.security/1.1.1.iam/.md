Perfect question 🔥 — **`iam:PassRole`** is one of the most *confusing* permissions in AWS, even for senior engineers.
Let’s break it down **step by step**, like a story, with diagrams and emojis so it finally sticks in your mind forever 😄

---

# 🧠 What is `iam:PassRole`?

Think of it this way:

> 🧑‍💻 You can **use** a role in AWS *only if* you’re allowed to “**pass**” it to a service that will act with that role’s permissions.

In other words:
You’re not “assuming” the role yourself — you’re **handing it over** to another AWS service (like EC2, Lambda, ECS, or Glue) so *that service* can act as that role.

---

# 🎬 Real-Life Example: Lambda Needs Permissions

Let’s say you’re Hady again 🧑‍💻 and you create a Lambda function.

You choose this IAM role in the Lambda setup:

> `LambdaExecutionRole`

That role will later be used by AWS Lambda runtime to perform actions like `s3:GetObject`, `logs:PutLogEvents`, etc.

But here’s the trick 👇

Even though the Lambda service will use that role, **you** are the one *attaching* it.
So AWS asks:

> “Is Hady allowed to **pass this role** to Lambda?”

If not — you get an error like:

```
User is not authorized to perform: iam:PassRole
```

---

# 🧩 The Permission You Need

To let a user (like Hady) pass a role to a service,
you must give them **`iam:PassRole`** permission on that role.

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::123456789012:role/LambdaExecutionRole"
}
```

That means:

> “Hady can hand over this specific role to AWS services.”

# 🚦 When Do You Need `iam:PassRole`?

You need `iam:PassRole` **anytime you attach a role to an AWS service**.

✅ **Common examples:**

| Service              | Action that triggers `PassRole` check                     | Example                                                                |
| -------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Lambda**           | Creating/updating a Lambda with `--role`                  | `aws lambda create-function --role arn:aws:iam::123:role/MyLambdaRole` |
| **EC2**              | Launching an instance with an IAM Role (Instance Profile) | `aws ec2 run-instances --iam-instance-profile Name=MyEC2Role`          |
| **ECS**              | Assigning a Task Role                                     | `aws ecs register-task-definition --task-role-arn arn:...`             |
| **Glue / SageMaker** | Starting jobs or notebooks with an IAM Role               | `aws glue create-job --role arn:...`                                   |
| **CloudFormation**   | Stack assumes roles for deployments                       | `aws cloudformation create-stack --role-arn arn:...`                   |
| **Step Functions**   | State machines execute roles                              | `aws stepfunctions create-state-machine --role-arn arn:...`            |

---

# 💡 Important Difference: `PassRole` ≠ `AssumeRole`

| Concept              | Who acts as the role?                              | What permission you need |
| -------------------- | -------------------------------------------------- | ------------------------ |
| 🧍‍♂️ **AssumeRole** | **You (the user)** assume the role yourself        | `sts:AssumeRole`         |
| 🤖 **PassRole**      | **An AWS service** assumes the role on your behalf | `iam:PassRole`           |

So:

* `AssumeRole` → “Let me **become** this role temporarily.”
* `PassRole` → “Let this **AWS service** use this role.”

# 🧱 Example: Hady Creates a Lambda

### Step 1: The Lambda role (trusted by Lambda)

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "lambda.amazonaws.com" },
  "Action": "sts:AssumeRole"
}
```

### Step 2: Hady’s IAM permissions

Hady needs both:

* Permission to **create Lambda**
* Permission to **pass** the role

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Action": ["lambda:CreateFunction"],
      "Resource": "*",
      "Effect": "Allow"
    },
    {
      "Action": ["iam:PassRole"],
      "Resource": "arn:aws:iam::123456789012:role/LambdaExecutionRole",
      "Effect": "Allow"
    }
  ]
}
```

# 🧯 Security Best Practices

| Tip                                   | Description                                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 🎯 **Restrict `iam:PassRole` by ARN** | Never give `Resource: "*"`. Limit to specific roles.                                                   |
| ⚠️ **Use Conditions**                 | Restrict who/what service can use `PassRole`. Example: `"iam:PassedToService": "lambda.amazonaws.com"` |
| 🔍 **Audit PassRole usage**           | Check CloudTrail for `iam:PassRole` events to see who passed which role to what service.               |
| 🧱 **Separate roles**                 | Create different roles for EC2, Lambda, etc., to avoid privilege escalation.                           |

Example with condition 👇

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::123456789012:role/MyLambdaRole",
  "Condition": {
    "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" }
  }
}
```

That means:

> “Hady can pass this role *only* to the Lambda service — not EC2, ECS, or others.”

# 🧭 TL;DR (Quick Memory Trick)

| Keyword        | Meaning                           | You’re Giving Role To |
| -------------- | --------------------------------- | --------------------- |
| **AssumeRole** | You become that role              | Yourself              |
| **PassRole**   | You let AWS service use that role | AWS Service           |

💬 **Remember:**

> 🗣 “You *pass* a role to a service, not to yourself.”
